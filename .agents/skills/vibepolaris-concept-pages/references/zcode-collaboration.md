# zcode 协作模式

仅在用户要求 zcode 协作时读取并启用。本模式服务于当前词条任务；沿用已有授权和项目流程，不把维护模式本身当成已执行的协作。

用户提供的模型为 Qwen3.8-flash-next，偏好是响应快。2026-09-27 本机 ZCode 界面显示 `Qwen3.8-Flash-Next-FP8`；这是当时的界面标识，不是能力评测或未来环境保证。按任务大小利用快速往返，具体产出仍需复核。

## 配套 Skill 与派发模式

让 zcode 读取 [vibepolaris-zcode-partner](../../vibepolaris-zcode-partner/SKILL.md)，每次指定一个模式。这是 VibePolaris 项目级 Skill，仅随本仓库及其独立 worktree 使用，不安装到用户级目录或 ZCode 全局配置。角色行为与返回格式集中维护在该 Skill；本文件只约定主助手如何安排、提供材料和回收结果。

不要假设 ZCode 自动发现 `.agents/skills`。发送前解析实际绝对路径，在任务首句要求读取该文件并简短确认模式和实际输入；语言模式还需可读的 `humanizer-zh`。若独立 worktree 尚未包含最新版，将 `vibepolaris-concept-pages`、`vibepolaris-zcode-partner` 和 `humanizer-zh` 的当前版本一并同步到该工作区，或显式提供原工作区的只读路径。文件不可读时提供完整规则文本；只发送技能名称不算确认加载。

| 模式 | 提供的材料 | 主助手重点核对 |
| --- | --- | --- |
| `inspiration` / 灵感 | 核实后的核心机制、读者目标、场景限制 | 是否熟悉、准确，是否呈现因果；候选的误导风险与待核实判断 |
| `reader` / 读者 | 读者背景与完成的正文或可访问页面，不附作者的解释或预判问题 | 对应原句的理解与追问；哪些确为缺失前提，哪些只是进阶兴趣 |
| `language` / 语言 | 当前成稿、humanizer-zh 和必须保留的信息 | 原句与局部改写是否保留事实、详细解释、技术限定和引用 |

资料整理、代码层演示审读或局部实现可以另行派发，但不属于这个三模式 Skill；按实际授权给专门任务与文件范围，不让读者角色顺便检查源码。

按词条需要选择任务。协作模式下，新增或大改正文优先安排成稿读者试读与一次语言交叉检查；构思困难时先请 zcode 提供灵感。局部实现只在产品实现已获授权、边界清楚时派发。简短改写由主助手直接做，已有有效审读结果无需重复获取。

## 灵感、成稿追问与去 AI 味

灵感阶段给出事实边界并保留探索空间；主助手核实后选择候选。成稿试读使用干净的协作上下文，优先提供可访问页面；不能查看页面时提供完整正文与关键状态，并标明覆盖范围。不要把主助手的设计意图或预期答案一并发给读者角色。

派发网页试读前，主助手先确认准确地址可用、关键按钮能推进状态，不能只确认服务端正文已显示。请 zcode 区分实际看到的画面、读取的正文和未操作的推测；关键交互疑问要结合截图或真实操作复核。只收到 DOM 文本时，不能据此断言文字可见、元素被遮挡或按钮会跳页。提供文字材料时，按“操作 → 当时可见状态”配对，不把互斥状态拼成一份同时可见的文字清单；文字审读不能记为页面交互试读。

收到追问后，先复现它指向的位置，再判断处理方式：缺必要前提就补正文；讲过但找不到就调整位置或称呼；画面传达错误关系就改画面；进阶兴趣放扩展；模拟误判说明理由、不改稿。不因模型提问就继续加字。必要时用一个不附答案的新场景或条件变化检查文章是否给了判断依据，允许模拟读者回答“文中没有讲清”，不把复述术语当成理解证明。

补齐内容后，主助手使用 [humanizer-zh](../../humanizer-zh/SKILL.md) 润色，再派发 `language`。以更新后的页面或重新取得的完整正文为输入，不只给上一轮粘贴草稿换一个角色开头。可以在同一草稿上并行收集初步意见，但后续新增、改动的关键句仍由主助手审读；有具体疑点才补一轮局部语言检查，不默认重审全篇。保留读者问题以核对修改，不让编辑意见污染独立试读。

反馈数量由实际问题决定，提示词可以限制篇幅，不规定必须提出几条。语言修改要有具体收益：指代更清楚、句子更顺或去掉了真正重复的信息。必要的三项列举、因果解释和边界说明不能仅因句式整齐而被改掉；主助手最终核对技术含义和讲解完整性。

## 主助手承担的工作

- 确定读者目标、必要前提、准确解释与教学主线，选择采用哪个场景及交互。
- 检索并实际读取原始资料，核实 zcode 整理的引用与技术结论；模型记忆或候选链接不算已核实来源。
- 合并编辑意见与实现，检查实际文件差异，执行本次必要构建和浏览器验收，按项目规则处理 DP、Git 与发布。
- 把模拟读者反馈当作发现问题的线索；有真实读者观察时以实际表现修正推测，不按模型评分宣布教学成功。

## 派发与回收

1. **确认真实入口。** 优先使用当前可调用的 ZCode 专用工具或已确认的 CLI；桌面环境可通过可用的电脑操作工具读取 ZCode 项目、会话与模型。不要臆造 `zcode` 命令、API、模型别名或后台认证方式，也不使用 Codex 内部代理冒充 zcode。没有可用入口时说明情况，给出可转交的任务文本并继续独立工作。
2. **给最小上下文。** 一个任务只负责一个明确结果。使用适合本任务的协作会话；盲读避免沿用已讨论作者意图的长会话。给当前版本的草稿或准确文件路径，以及必要事实与约束，不复制无关历史、凭据或整仓内容。页面会随代码更新时，在工作笔记记下审读版本或修改时间，审读期间不改动同一段材料。
3. **划清读写范围。** 审读与候选生成默认只读、不运行命令。实现任务写明工作目录、允许文件、可运行的检查与禁止改动；主助手和 zcode 不同时编辑同一文件。存在用户未提交修改或并行实现时，使用独立 worktree，或让 zcode 只返回补丁建议。DP、分支切换、提交和发布由主助手统一处理。
4. **推进独立工作。** zcode 审读时，主助手可核实来源或处理不重叠的内容。等待时间适度，避免反复轮询；获得结果后先核对关键问题是否真实存在，再决定采纳、追问或放弃。
5. **有问题才迭代。** 需要补充时指出具体缺口，只追问受影响部分。无新证据不反复整篇审读；输出无法使用、持续偏题或入口失败时收回该子任务，由主助手完成。报告实际拿到和采用了什么，不将已发送、正在运行或助手自述完成写成验收通过。有效记录只需会话标识、角色、输入版本与形式、关键反馈及处理；网页操作覆盖与文字审读范围分开写，无须复制完整聊天记录。

## 可直接裁剪的任务文本

发送前填入当前内容并删掉不适用项，避免只说“优化一下，让小白能懂”。

```text
请先读取 [vibepolaris-zcode-partner/SKILL.md 的实际绝对路径]，按指定模式完成本轮任务。
模式：[inspiration / reader / language，选择一项]
词条与目标：[读者在哪里遇到这个词，读完应能作出什么判断]
读者背景：[已知内容；默认会用浏览器和 AI 聊天，没有编程经验]
输入：[本轮实际材料、版本或准确路径；标明网页、正文或按状态配对的画面；reader 只给读者可见内容]
开始时简短说明模式与实际读取的材料，返回时说明实际覆盖范围。只读并在对话中返回本模式结果，完成后停止；有多少有效问题就报多少。
```

不把作者希望听到的结论放进读者提示词。回收后复核输入是否仍是当前版本，保留有用的采纳或不采纳理由；无新问题时结束，不为显示工作量反复改稿。

实现任务另附状态变化、可见证据、停止与重置的场景契约。回收时核对正文、演示与样例是否仍一致；任务外的关联问题由主助手判断处理，不要求 zcode 越过文件边界自行修复。

## 仅在比较多个模型候选稿时

开始前固定代码基线、完整 Skill 版本、读者目标、任务范围和协作条件；记录模型与推理等级，分别使用独立 worktree。不要只写“都用最新版”，后续修改 Skill 不追溯覆盖已完成样本。额外要求避开某个场景、提供不同形式的审读材料等，都记为条件差异。

比较实际正文、关键画面与反馈处理，重点看概念价值、必要前提、因果链、图文一致性和自然表达。字数、引用数量、反馈条数或提交与否不单独代表质量；只有采用可比计时方法时才比较速度与成本。单个词条、不同推理等级或 Skill 版本的结果只支持本次候选选择，不写成模型通用排名。没有真实读者时保留该限制，不自动再跑一轮模型实验。
