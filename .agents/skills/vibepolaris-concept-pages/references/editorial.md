# 正文与资料研究

在新增概念解释、重写文章或检查事实与引用时阅读。本文件不要求只改动效的任务重新检索所有资料。

## 从一个真实困难开始

默认面向会用浏览器和 AI 聊天、但没写过代码的读者。先记录他遇到词语时的原话与眼前任务，确定本页读完后能解决哪个疑问。检查例子是否也需要学习：修服务、读日志、执行脚本都可能是前置障碍。可以换成熟悉的任务，也可以当场补齐必要背景，不把已有四页的场景当成零基础保证。

先确定读者能理解的情境，再挑出这个概念在其中解决的部分。四篇文章共用修服务案例，但观察角度不同：

| 词条 | 读者要辨认的机制 | 讲解的边界 |
| --- | --- | --- |
| Harness | 谁组织模型调用、工具执行、结果保存与检查 | 模型提出请求，工具做具体操作，Harness 协调；各资料对名称的划分可能不同 |
| 工具调用 | 请求怎样交给执行程序，结果怎样回到模型 | 回复中出现函数名不代表已经执行；一次调用不等于整个任务完成 |
| 上下文 | 这一轮实际提供了哪些信息 | 外部存储、历史记录、训练知识、窗口容量与当前输入不是同一件事 |
| 智能体循环 | 新结果如何改变下一次操作 | 增加轮数不等于进展；达到上限不等于任务成功 |

迁移到其他词条时重新选择场景，不强行把缓存、CSS、Git 等概念都解释成修服务。若复用同一案例，保持文件名、输入、结果和术语含义一致。

再问一句：没有这个概念，同一件事还能怎么做，它具体改变了什么？例如，演示“确认后创建日程”主要说明工具执行和操作确认；讲 MCP 还要解释为什么共同约定能减少不同应用与服务反复适配的工作。用相邻概念作例子时补足这层关系，避免读者记住了案例，却没明白为什么需要当前词条。不要求每篇都新增对照图或独立章节。

## 按读者的追问组织讲解

先写一条简短的追问草稿，再据此写自然正文。可以从以下几类反应中选择实际相关的，不要求固定顺序、数量或全部出现：

- “这个词是什么意思？”：先给出准确且能继续解释的一句话，避免用另一个陌生词替换它。
- “你说的这个词又是什么？”：定位解释里新引入的前提，在原地解释充分，需要时补一个短例子。
- “能举个我见过的例子吗？”：选读者熟悉的真实任务，明确谁做什么、东西在哪里、结果怎样出现。
- “所以就是……？”：写出读者可能的粗略复述，保留正确部分，修正会影响后续理解的误解。
- “那和我知道的另一个东西有什么区别？”：只解释眼下容易混淆的关系，不立刻展开整张术语网络。
- “我现在做的事情，哪一步会用到它？”：回到最初任务，说明读者凭这个概念能判断或处理什么。

例如，解释 API 时，读者可能卡在“接口”，需要先看天气 App 获取天气的例子；随后可能把 API 理解为存放天气数据的地方。下一段应接住这处混淆。这个例子用于说明追问方法，正式文章仍需核实技术表述。

每个关键段落检查：读者读到这里已知道什么，刚新增了什么，下一步最可能在哪里断开。用实际草稿中的词句定位问题；“再简单一点”这样的反馈要落实成缺少的前提或不明确的关系。避免先写专家式长文，再只把术语替换成口语。

陌生术语出现时，检查读者眼下为什么需要它。例如“本机进程通过标准输入输出通信”又引入了进程、标准输入和输出；可以先讲“AI 应用按配置启动电脑上的服务程序，两个程序在本机传话”，再在需要对照配置时给出 `stdio`。暂时不影响理解或判断的分层名词、方法名与实现变体放到相应补充处；详细应体现在前提和中间步骤充分，不是提前列完专业名词。

追问只是编写时的推演，不冒充访谈记录，也不强制把网页做成问答列表或聊天界面。读者未必会提出理想问题，常见反应也可能只是“还是没懂”。盲读仅提供读者背景与草稿，不附作者的解释；这有助于发现问题，但模型不能证明真实小白已经理解。

### 例子、类比与深度

- 用一个主要例子讲完核心过程；读者建立基本理解后，再用不同场景检查是否理解了共同机制。
- 类比明确对应真实对象与动作，及时回到技术含义；只提醒会造成误解的类比边界，不为每个比喻追加长篇免责声明。
- 必须理解的前提与关键因果关系留在正文。术语卡片补短释义，折叠区承载旁支细节，不让读者为了读懂一句话连续跳转多个词条。
- 正文优先写得详细、通俗。把为什么需要、谁做什么、过程中的变化、结果依据、容易混淆处讲开，不预设字数上限，也不把长文自动压成摘要。每段应增加事实、解释、例子或有用的区分；重复结论与空泛扩写可以删除。
- 用段落、标题和递进例子承接长内容。核心过程的详细解释常驻；代码、历史和实现变体按读者需要安排位置，不能把“小白需要读的解释”全部收进折叠区。正文可以充分展开，演示内部仍保持极简。

## 资料研究步骤

1. 每个完整词条至少使用四份已实际阅读的公开参考资料（用户确认的质量要求）。围绕核心机制和易混淆边界检索，不以无关链接凑数；不足时补研究，不虚报满足。简单文案调整无需为数量重做无关研究。
2. 实际打开来源，确认它支持哪条论断；搜索摘要不能替代正文。原始资料足够时停止扩展，存在分歧时对照不同实现或作者。
3. 区分通用机制、具体厂商接口、研究方法、作者经验与本站教学简化。例如 ReAct 是相关方法，不能把所有循环都说成同一种提示格式。
4. 记录作者或机构、标题、规范 URL、能确认的日期、支持的内容及限制。无发布日期就留空；阅读日期不能冒充发布日期。
5. 新增精确字段、版本限制或数量时核查现行官方文档。资料访问受阻时注明证据缺口，不补写没读到的内容；仍可推进独立的版式工作。

技术解释优先使用规范、官方文档、原始论文、作者博客、大学或开源项目的公开课程。书籍使用出版信息和合法公开章节；付费书未实际读到的章节不能当作已核对证据。用自己的话组织，短引文才加引号，不复制整段书摘。

已有资料入口在 `lib/harness-references.ts` 和 `lib/concept-article-sources.ts`。它们包括 Anthropic 的智能体、上下文与长任务文章，Claude 工具文档，Hugging Face 课程，ReAct 论文，LangChain 的上下文文章及 Harness 页引用的公开工程资料。新增或修改事实时仍要核对原文，不能仅凭既有标题推断结论。

### 最小来源笔记

只维护对本次写作有用的信息，可留在已有需求记录或工作笔记中：

| 正文要表达的内容 | 直接支持它的资料 | 适用限制 | 段落锚点 |
| --- | --- | --- | --- |
| 例如：工具结果要与调用对应 | 已读的接口官方文档与 URL | 字段名属于该接口 | `<slug>-result` |

没有正文对应关系的来源不放进书目；一个来源可以支持多处正文，一个论断也可以引用多个来源。

## 文章先成立，动画再辅助

情境、准确解释、可观察过程、边界、失败或后续用于检查内容是否完整；实际顺序由读者追问与必要前提决定，不要求照抄成五个章节。

常驻正文应足够回答：

- 这个概念在做什么；输入从哪里来，结果到哪里去；
- 例子中实际发生了什么，读者凭什么得出结论；
- 它与近邻概念的区别，以及什么情况下不能套用；
- 需要继续了解什么、原始资料在哪里。

动画前交代任务和输入，动画后解释结果与边界；不要把同一句话再重复成动画脚注。隐藏术语卡片用于局部名词，折叠内容用于旁支例子和详细记录。定义和主要因果链不能只藏在卡片、动效或折叠区里。

可以将空间关系、状态转换、代码差异和信息选择做成图；不能因为图更好看就删除读懂它需要的解释。反过来，能通过对象变化说清的步骤，不再叠加一整段说明。

## 中文表达与标题

标题直接点出正文内容，例如“一次日志读取”“窗口与外部资料”“循环何时结束”。问题句只在问题本身有价值时使用，不让整篇文章变成连续设问。

用具体主语和动作：谁读取、谁检查、谁保存、谁重新决定。删掉“真正的奥秘”“解锁无限可能”“一文读懂”等宣传话术，以及机械的三段式和否定式排比。保留理解所需的细节，不能把“去冗余”变成“只剩口号”。

重点加粗用于定义、责任边界、验收依据或容易误解的结论。避免整段加粗，也不要仅为视觉变化随机加粗。代码字段用行内代码；结果数值保持一致，教学样例不得伪装成实时测量。

### 使用 humanizer-zh 与交叉审读

新增或实质重写词条正文时，读取并应用 [humanizer-zh](../../humanizer-zh/SKILL.md)。普通错字修正不启动全文重写。用户要求的详细、通俗优先：保留必要的逐步讲解、因果连接、类比对应和技术限定；不要机械执行“信任读者”“缩短句子”“避免三项”等建议而删掉教学内容。

先补齐理解缺口，再检查语言。重点处理空泛评价、夸大意义、反复总结、模糊归因、整齐划一的段落和刻意制造的金句；用具体对象与动作替换空话。同一概念保持稳定称呼，句式和段落长短服从内容。通俗表达仍须准确，不靠网络口头禅、故意出错或虚构个人经历制造人味。

启用 zcode 时，按 [协作规范](zcode-collaboration.md) 做成稿读者试读和语言交叉检查。主助手写的内容可交 zcode 定位问题；zcode 提出的改写由主助手按 `humanizer-zh` 与来源复核。问题须给出原句、原因和局部改法，不只评价“有 AI 味”或把全文重新生成一遍。

润色后检查事实、因果顺序、限定条件、例子细节、术语含义和引用仍然一致。必要的“可能”“在这个例子中”不能作为虚词删掉，也不为让文字更具体而新增未经核实的数据。主助手裁决相互冲突的建议；只复查实质变化的段落，不反复全篇改写。评分仅能作为内部提示，不能证明文章由谁写作或是否通俗。

## 引用和名词解释

- 事实对应段落添加稳定 `id` 和 `vp-citation-target`，来源的 `citations` 指向这些 ID。
- 正文用 `ArticleCitation` 或 Harness 当前的引用组件生成角标，编号跟随来源列表；不要手写两份独立编号。
- 角标放在支持的句子或段落附近。段落中混入不同来源时拆分对应关系，避免一个编号看似支持整段所有结论。
- 书目展示作者或机构、文章标题、可确认日期和完整 URL。用旁边的小三角点击展开本文引用摘录，鼠标经过不自动展开，不显示“本文 X 处”徽标。
- 摘录来自当前正文，不复制一份会过时的文案。点击摘录返回真实段落；目标在折叠区内时先展开，并在收起动画结束后定位。
- 删除、移动或改写段落时同步来源映射。不要为了让引用非空，把来源挂到无关句子上。
- 难懂且值得解释的词使用 `InlineTerm`：主题色虚线下划线，点击展示旁边的短卡片，可继续进入详情。不要把每次重复出现的词都变成按钮。

完成后做一次不播放动画、不展开补充内容的通读。若仍说不清定义、过程和边界，先补文章，再调视觉。

再准备一个改变关键条件或换场景的短例子，检查正文是否提供了作出判断的依据。它可以只作为编辑审读材料，不必加入网页。若实际请目标读者试读，记录其原话、卡住的位置与复述中的误解；把这些观察与主助手或 zcode 的推测分开。
