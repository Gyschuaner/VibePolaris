# VibePolaris 概念词条设计

让读者能用自己的话解释概念的作用，预测改变一个条件后的结果，并判断一个新例子是否适用。**正文详细、通俗、自然，能够独立读懂；动画让机制更容易理解。** 愿意多用篇幅讲清前提、过程、例子和边界，不为追求简短省略解释。延续站点气质，核心场景根据概念重新设计。

本 Skill 来自四页实际迭代：`agent-harness`、`tools`、`context`、`agent-loop`。它们是经验样本，不是四套只能套用的模板。开始时告知用户正在使用本 Skill。

## 范围与入口

- 新词条或完整重做：走下面的完整流程。
- 只改文案、首图、动效或排版：先检查已有内容，只执行受影响环节；保留已经确认的部分。
- 批量做多个词条：先写一张机制差异表，再实现，避免多个页面只换名词。
- 只要求方案时交付方案；要求实现时完成可运行页面和必要验收。已有明确方向与授权，不为固定的提案数量重新等待确认。

项目研发记录、Git、发布和权限遵从当前根目录 `AGENTS.md`，不在本 Skill 复制一套状态流。写代码时使用项目要求的 `ponytail`；新增或实质重写词条正文时，读取并应用 [humanizer-zh](../humanizer-zh/SKILL.md) 做中文审读，具体边界见 [正文与资料研究](references/editorial.md)。本 Skill 的维护本身不触发产品构建、部署或新建研发需求。

## 可选：zcode 协作模式

用户要求 zcode 协作时，读取 [zcode 协作](references/zcode-collaboration.md)。同一任务已启用后，按既定范围继续，不逐轮重复确认；普通小改动由主助手直接完成。仅讨论或维护这个模式不等于已派发任务。

派发灵感、成稿读者或语言审读任务时，让 zcode 读取配套的 [vibepolaris-zcode-partner](../vibepolaris-zcode-partner/SKILL.md)，并指定一个模式。主 Skill 负责安排与回收，配套 Skill 约定 zcode 本轮怎样执行；发送时提供实际可读的绝对路径，不假设接收方已自动加载。

利用快速模型提供灵感，在成稿后扮演读者提出追问，并交叉检查中文表达；也可分担资料整理、演示审读或局部实现。主助手负责核实来源、决定教学主线、整合和验收。读者试读与语言编辑分别给任务，避免模型一边扮演小白一边替作者补全解释。协作通过实际可用的 zcode 入口完成，不把 Codex 内部代理冒充为 zcode。模型模拟的读者反馈只作编辑线索。

## 工作流程

### 1. 看现状，确定读者要学会什么

读取当前页面、路由和相关组件；已有页面先观察真实浏览器和用户截图。核对用户最新反馈，不把历史实现当成最终要求。

默认读者会浏览网页、会和 AI 聊天，但没有编程经验；用户给出其他背景时以用户为准。先找到读者遇到这个词时可能说的原话，例如“AI 让我配置 API，这是什么”。用简短工作笔记确定：

- 读者在哪里遇到这个词，读完应能做出什么判断；
- 哪些知识可以假定读者已知，例子本身又依赖哪些陌生概念；必要前提在原地补齐；
- 一句准确解释、最容易混淆的相邻概念，以及没有它时同一件事还能怎样做、它具体改善了什么；
- 一个适合贯穿文章的真实场景；
- 场景里谁做什么、什么东西会改变、什么结果能够证明变化；
- 本次范围、保留内容和适用的验收项。

按 [正文与资料研究](references/editorial.md) 推演读者追问：读完一句解释，他可能卡在哪个词，会怎样说“所以就是……”，下一段要接住哪处误解。提问顺序是待验证的写作假设，不是所有读者必经的固定步骤。这些笔记供设计判断，不必全部展示成页面小字，也不必另建正式文档。

### 2. 研究资料，先写出能读懂的文章

涉及新增概念解释或事实变化时，阅读公开原始资料，建立“论断—来源—正文位置”的对应关系。优先规范、官方文档、原始论文、作者技术博客和合法公开书摘；确认资料讲的是哪个实现、版本与适用范围。

按 [正文与资料研究](references/editorial.md) 组织内容。用核实后的事实修正追问与类比，沿读者当前能理解的内容逐步讲清定义、过程、边界与结果，再决定哪些关系值得画出来。核心例子尽量贯穿主线，读懂后再用新例子检查能否迁移。保留足以独立理解的常驻正文；补充术语、旁支例子和详细记录再按需收起。只改视觉且既有事实未变时，不重做无关研究。

充分写出读者需要的中间步骤，长度随解释需要决定。成稿后先接住读者追问，再用 `humanizer-zh` 审读表达；启用 zcode 时按协作规范交叉检查。润色后复核事实、限定条件、例子和引用，避免删掉使小白能够理解的细节。

### 3. 先选机制，再选画面

按 [演示、视觉与代码接入](references/interaction-design.md) 选择对象、操作和空间关系。不要先选“三个图标加曲线”，再向里面填文字。

每个演示先描述：**初始对象 → 用户操作 → 对象或状态变化 → 可见证据 → 后续或停止**。有异步执行时，再写清等待状态和结果何时才允许出现。核对容器、连线与对象归属是否和正文一致；演示可以借助相邻概念，但要让读者知道本词条在其中具体做了什么。

指出演示接住哪一个具体疑问，例如“拿掉这份材料，为什么回答会变”。改变一个关键条件，让读者能把结果差异归因到这次操作；开关、移动与点击应表达概念本身。完整正文仍承担解释，页面不因追问设计而自动增加聊天框或测验模块。

多页同时设计时，比较首图构图、主体交互、正文节奏三项。若去掉文字后几乎无法区分，先修改核心表现；调整颜色、图标或标签不足以解决同质化。

### 4. 编排文章，复用公共阅读能力

依据内容选择长短段落、侧栏讲解、对照、代码与结果、重点引文、局部星图等形式，不要求每页全部出现，也不让每节都重复“标题—两段话—方框—下一步”。

复用已有主题变量、语义图标、目录、术语卡片、引用和星图数据。演示所有状态都约束在正文宽度内。首图应提前展示概念的机制，允许轻量的有限动画，不能只是装饰或放大一组流程图标。

品牌星星用于品牌标识、标题与概念星图；文件、工具、模型、检查等职责用语义图标。用留白和字体层次组织内容，避免密集横线、无意义边框和重复辅助小字。

### 5. 实现顺序与动效生命周期

先让状态和结果正确，再添加移动、淡入淡出或形变。工具请求、实际执行、返回结果与后续判断分别建模；上一段文字流式输出结束后，才能出现依赖它的工具动作。

展开与收起都要有过渡；重置、切换场景和修改输入不能把旧结果冒充本次结果，也不能遗留旧定时器。区分本轮进度、历史结果和已发生的数据修改，不把断开连接或撤销权限画成撤销过去的操作。有限自动播放结束后停在有意义的状态，支持手动推进或重播；离开可见区域和进入后台时暂停。减少动态效果时直接提供可读、可操作的状态。

具体的聊天、引用、目录、术语卡片、星图和性能注意点见 [交互规范与常见问题](references/interaction-design.md)。

### 6. 按范围验收，完成后交付

实现前从 [验收标准](references/acceptance.md) 选本次适用项。代码先构建；交互改动再按项目规则用真实浏览器检查受影响流程。不同视口、失败分支和键盘行为按实际改动覆盖，不把清单机械地扩展成全站回归。

查看真实画面和过渡中间状态，不只看 DOM 文本或构建结果。修复具体失败后回归对应项；检查通过且没有新信号就停止追加验证。

内容审读检查读者能否复述作用、解释变化、判断新例子。主助手或 zcode 的模拟审读用于发现理解断点；只有实际目标读者参与过，才能报告读者验证结果。没有真实读者时如实保留这个证据缺口，不自动扩展成用户招募任务。

语言验收定位具体生硬表达、套话和机械结构，并确认修改保留了充分解释。模型评分或所谓 AI 检测分数不作为通过依据；没有新问题时停止往返润色。

交付可打开的本地地址、各页实际差异、验证证据和未验证部分。区分本地完成、Git 集成、远端部署与用户设计验收；需要进入哪个阶段，按当前 `AGENTS.md` 执行。用户新反馈只在有复用价值时回写本 Skill，避免积累一次性参数。

## 本次经验的使用边界

- 四页统一的是阅读质量和基础交互，不是动画形状、章节数、卡片数量或控制器位置。
- 保留当前 `relatedSlugs`、正文锚点和引用映射；新增关系要有概念依据，不为凑星星自动按分类补边。
- `docs/design/term-experience-authoring.md` 描述较早的数据驱动体验。若使用该数据结构，遵守实际 schema；其中固定帧数、来源数量、问题式开头和测验模块，不作为这四页式独立文章的通用要求。
- 默认不恢复四页已移除的测验区、循环代码大模块、“本页”目录标题和“本文 X 处”引用徽标；用户明确需要时再按新目标设计。
