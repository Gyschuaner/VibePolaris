### API 的可执行数据

内部 A：`{ id: 42, title: "星空手记" }`；内部 B：`{ book_id: 42, display_name: "星空手记" }`。外部约定始终是 id 为整数、title 为非空字符串。开启映射时两种内部结构都输出同一份外部数据；透传 B 时返回的文本仍可能是合法 JSON，但调用方取不到 title，不生成成功书签。不要把 HTTP 200 当作字段兼容的证明。

结果由真实对象与字段检查决定，不切换一段预写结论冒充执行。内部选择/映射策略变化使上一次调用失效，保留旧 DOM 完成淡出；点击交给调用方后才显示此次结果。重置恢复 A、映射开启、尚未调用。没有网络、凭据输入和任意代码执行。

### Endpoint 的有界匹配

本例只声明 GET /books、POST /books、GET /books/42。矩阵还展示 DELETE 行与 /authors 列，方便观察未匹配组合。支持两个 `example.com` 服务基址以区分环境，但只构造地址，不能真的请求它们。选中格子改变方法与路径，再点击匹配，结果指向声明的 operation；不把“找到处理入口”显示成“图书已创建”。

若呈现 405/Allow，必须明确是教学接收端约定并与实际声明一致；不要假装实现了完整HTTP服务器或自动 HEAD、OPTIONS 行为。更简单的主画面可以只显示“入口已找到/该路径未声明此方法/路径不存在”，把规范状态码放到正文。无效输入不触发任何写入。键盘和手机用同一组语义按钮；矩阵在窄屏按路径分组，不整体缩小。

### REST 的有限状态机

资源为预约42，初始 pending。先读取表示，再从返回的 actions 描述显示确认/取消；动作内容包括 rel、方法、目标和必要字段，客户端按本例已知媒体类型/关系含义使用，不从按钮标签猜URL。选择动作先验证当前服务状态，再更新资源并返回表示；确认、取消都是停止态。

增加一个“服务端使预约过期”操作，仅改变服务资源，不自动改掉客户端手里的旧表示。此后点击旧确认会得到本例409和 expired 表示；不显示已确认。重新获取直接更新到最新表示。重置清空客户端快照，恢复 pending。

actions、rel等字段为本站教学表示约定，不是REST规定的JSON字段。它们用于解释“收到可执行选择再继续”；不声称这个小模拟实现了完整REST。所有数据在浏览器内，状态码为本例选择；不接入真实预约服务。

## 常驻正文初稿

### API 接口：程序之间怎样约定

一张书签要显示编号和书名。页面不必知道数据来自哪张表，却必须知道该怎样请求、返回字段叫什么、失败时怎样处理。API规定了这些交互方式；HTTP接口是其中一种，库函数和浏览器提供的功能也有API。

本例约定读取42号图书，成功结果包含整数id和字符串title。服务内部把title改名为display_name，并不必然要求页面跟着修改：服务可以在边界处继续输出title。试着切换内部存储，再比较“按约定映射”和“直接透传”。前者保持调用方依赖的结构，后者让内部字段变化穿过边界。

API不能只写成功样例。调用条件、身份与权限、输入限制、可能失败的状态和返回结构，都影响调用方如何继续。文档可以用OpenAPI表达，但写进文档并不代表服务已正确实现；请求和响应仍需要验证。

兼容性也不是“新增字段永远安全”。如果调用方允许忽略未知字段，增加一个字段通常不会挡住旧逻辑；严格拒绝额外字段的客户端可能不同。删除title、改成嵌套对象，或改变字段含义，都需要检查已有调用方。稳定的是承诺的交互规则，内部存储结构可以演进。

### 端点：一个地址上的具体入口

同样写/books，GET和POST表达的操作不同；同样是GET /books，换一个服务基址也可能访问另一套系统。核对一次HTTP调用时，要把基址、路径和方法放在一起看。

不同文档对endpoint一词的粒度不完全一致，有的强调可访问的位置，有的连同方法称一个端点。OpenAPI把一个路径下的GET、POST等分别描述为operation。实际对接时，与其只争论“算几个端点”，更有用的是明确完整地址、方法、输入和预期结果。

矩阵中每个格子都是一个方法与路径的组合。GET /books和POST /books分别落到读取集合和创建处理入口；GET /books/42落到详情入口。演示只做匹配，不执行数据库操作。找到入口也不代表权限、输入或业务检查已经通过。

无法调用时先区分层次：路径没有入口，与目标不接受这个方法不是同一件事。HTTP用405表达已识别但不被目标允许的方法，并要求返回Allow；404可能与资源、路由或隐藏对象的策略有关，不能仅凭一个状态码断定根因。地址拼对只是起点。

### REST：资源的表示与后续操作

一个预约有稳定的标识，也有会变化的状态。/reservations/42标识这个预约；服务返回的JSON只是它某一刻的表示，不是资源本身，也不是数据库行必须原样暴露的证明。REST是组织这类交互的架构风格，不是一张URL命名表。

读取一个待确认预约时，服务可以连同当前状态提供接下来允许的选择。调用方理解表示格式和关系含义，再使用返回的目标发起动作，而不是把所有URL规则都硬编码在页面中。确认后，预约状态改变，新的表示也不再提供同一组选择。

可点击的旧选择不保证现在仍有效。让演示中的预约在服务端过期，客户端旧表示暂时不变；再尝试确认，服务会按当前状态拒绝并返回新表示。界面反馈需要依据执行结果，不能仅凭按钮还在就显示成功。

无状态也不等于服务没有数据库。预约可以持久存在；限制的是处理一次请求不能依靠服务替这个客户端偷偷记住上一轮会话步骤。请求应包含解释这次动作所需的信息，服务还需要按当前资源状态和访问规则检查它。

完整REST还包括客户端与服务端分离、缓存约束、统一接口、分层系统，以及可选的按需代码。统一接口涉及资源标识、通过表示操作、自描述消息和超媒体驱动。名词URL、JSON、四种HTTP方法都不能单独证明一个系统符合这整套约束。实际项目可以有意采用其中一部分，但应说清采用了什么。

GET的安全语义是调用方要求读取，不能让“打开预约详情”成为取消预约的命令。服务记录日志等附带行为不自动违反这一语义；不能把安全方法解释成“机器内部一位数据也不能改变”。
