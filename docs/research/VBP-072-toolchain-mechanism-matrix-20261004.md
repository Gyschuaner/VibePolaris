# VBP-072 工具链词条机制差异表

本批按 `vibepolaris-concept-pages` Skill 逐条完成，十条在完成后统一发布。每个词条先回答零基础读者在真实任务中遇到的一个问题，再用不同的可观察变化说明它在链路中的职责。

| 词条 | 读者任务 | 初始对象 → 操作 → 可见证据 | 边界与失败分支 |
| --- | --- | --- | --- |
| compiler | 为什么源代码不能直接交给目标机器？ | 源文件 → 编译检查并生成目标代码 → 错误停在输入，成功产物可运行 | 编译通过不等于业务正确；目标平台或运行时不兼容仍会失败 |
| interpreter | 为什么同一段源代码要在运行时被逐步读懂？ | 源代码 → 解析当前语句并执行 → 每一步都有输出或运行错误 | 解释执行不等于没有编译；现代运行时也可能 JIT，错误可能在运行时才出现 |
| transpiler | 为什么 TypeScript 能变成浏览器能运行的 JavaScript？ | TS 源码 → 去掉类型并改写语法 → JS 产物，类型检查另行显示 | 转译不负责类型正确性、依赖解析或打包；能生成 JS 不代表能运行 |
| build-tool | 为什么一次命令会串起检查、生成和产物目录？ | 源码与配置 → 按任务图执行 → 失败步骤阻断，成功得到可部署产物 | 构建工具负责协调流程，不自动证明需求、测试或部署安全 |
| bundler | 为什么浏览器收到的文件和源码目录不一样？ | 多个模块及依赖 → 解析并合并/拆分 → 浏览器可加载的产物与依赖图；按需块请求失败时主包仍保留 | 打包不等于类型检查或业务验证；动态导入、外部依赖和运行时路径仍有边界 |
| dev-server | 为什么保存文件后能立刻在本地页面看到变化？ | 项目根目录 → 开发服务器按需提供模块 → 浏览器请求得到最新模块 | 开发服务器只服务开发反馈，不等于生产服务器、构建产物或安全配置 |
| hot-reload | 为什么页面改代码后不用整页刷新？ | 已运行页面与模块 → 发送局部更新 → 保留可保留状态并显示新代码 | 状态无法安全保留、边界模块变化或错误时会退回整页刷新/报错 |
| hmr | HMR 具体是怎样把模块变化传给页面的？ | 文件变更 → 服务器推送更新消息 → 客户端接受/更新或失效 | HMR 是机制/API，不保证每个框架组件都能保留状态；生产环境通常不启用 |
| dependency | 为什么项目还需要别人写的包和它们的版本？ | 项目导入包 → 包管理器解析直接/间接依赖 → 安装树与锁文件可复现 | 依赖声明不等于安全或兼容；缺包、版本冲突、供应链风险都要单独处理 |
| semantic-versioning | `1.2.3` 里的三位数字怎样帮助判断升级风险？ | 当前版本与变更 → 按规则增加 major/minor/patch → 版本范围决定是否接受 | 规则是约定，不会自动识别所有破坏性变更；`^`、`~` 的范围要结合 0.x 和锁文件理解 |

研究来源优先使用 MDN、TypeScript、Vite、npm 与 semver 原始文档。正文的每个可核查断言都通过段落级 `Cite` 映射到对应来源；演示中的数字和状态均为固定教学数据，不冒充真实构建或安装结果。
