## 每篇实际审读

1. 完整读取文章的标题、summary、body、全部 sections、旧 explainer 和所附来源证据；再独立判断核心机制，不能由标题、旧 variant 或作者 rationale 直接推定。
2. 读取该 slug 的实际 `NewsMotionDesign` 全部字段及其实际场景组件。结合共享图形辅助函数、渲染分派、主题样式和父级播放控制，检查这些配置最终画成什么、哪些文字或边界真正可见。共享代码未改变时复用已读证据；仍逐篇核对其具体用法。
3. 用一两句真实读者追问核对：谁执行动作？哪个对象改变？为什么这个结果成立？未知、计划、人工决定或使用条件是否还在？问题必须对应本篇内容，不能全量粘贴同一句。
4. 新增或不确定事实回到必要的一手来源。以本篇事件当时的状态为准；不能用后续产品状态补成当日已实现。现有正文若与动效所需事实冲突，记录具体位置与证据交主代理处理，不擅改新闻，不因它已发布就默认正确。

重点判断：

- **对象与因果**：同一资料、权限、任务或产物是否可追踪；模型提出请求、框架执行、结果返回等角色是否被互换；复制是否被误画为删除，预测是否被误画为事实，候选补丁是否被误画为问题已修复。
- **事实边界**：公告与上线、计划与交付、许可与开放权重、筛查与诊断、评测与现实效果、申请与获批、容量与实际用量分开。事故不画成已经解决，政策不画成自动合规。必要边界不能只写在 rationale 中。
- **数值**：`values` 的单位、分母、时间、测试框架和比较对象须同口径且有正文或来源支持；柱长、计数或面积不能暗示无证据的比例。机制示意应与真实性能数据有可辨区别。
- **动作与表达**：2—4 个 items 是实际被操作的信息对象；连续动作解释机制。不能把正文换成三卡队列、编号步骤或逐段文字换页。只在妨碍理解时报告中文问题，避免宣传、抽象结论和重复脚注。
- **逐篇设计**：同一场景可以复用几何，但本篇的对象、动作、结果和构图必须有内容依据。对相邻新闻及同 scene/mood 的配置作对照，标出仅换名词而核心机制不符的具体 slug；不因有 32 个场景名就宣称风格多样已验收。
- **组件约束**：读取实际连续 progress 行为、对象显隐和端点；检查组件是否绕过父级计时、增加网络动作或忽略字段。窄屏重排、主要标签尺寸、键盘与减少动态先作代码判断，真实可读性和操作结果由主代理的浏览器证据确认。

## 紧凑逐篇格式

实际批次就绪后，在本目录 `reviews/YYYY-MM-DD.jsonl` 中一行记录一个 slug 的一轮审读。修订复审追加新轮次，不覆盖旧问题或旧哈希。以下仅为格式说明，**不是审读结果**：

配置到齐前，已完整读过的文章可先记入 `reviews/article-prereads.jsonl`，只记录文章哈希、机制约束和本篇读者问题，状态固定为 awaiting-design；这是预读证据，不计为设计复审通过。正式逐篇记录仍须结合实际配置和组件。

```json
{
  "eventDate": "YYYY-MM-DD",
  "slug": "<文章 slug>",
  "round": 1,
  "checkedAt": "<实际 UTC ISO 时间>",
  "scope": "static-content-and-code",
  "mechanism": "<审稿人独立写的一句核心因果>",
  "scene": "<实际 scene 值>",
  "mapping": "<本篇对象如何对应实际组件动作>",
  "questions": ["<本篇真实读者追问>"],
  "decision": "unverified",
  "issues": [],
  "followUp": [],
  "readObjects": [
    {"kind": "article", "path": "content/zh/news.json", "selector": "slug=<文章 slug>", "hashMode": "canonical-json", "sha256": "sha256:<实际摘要>"},
    {"kind": "design", "path": "<实际批次配置路径>", "selector": "<文章 slug>", "hashMode": "canonical-json", "sha256": "sha256:<实际摘要>"},
    {"kind": "scene", "path": "<实际场景组件路径>", "hashMode": "file-bytes", "sha256": "sha256:<实际摘要>"}
  ],
  "sharedReadRef": "<已实际读过的共享依赖记录；没有则为 null>",
  "browser": {"status": "not-reviewed", "evidenceRefs": []},
  "recheckOf": null
}
```

- `decision` 只用 `passed`、`needs-revision`、`unverified`。`passed` 在本格式中仅指该版本的静态内容与代码审读通过；不能写成构建通过、浏览器通过或整体交付。没有配置或组件的文章保留在待审清单，不创建空的 passed 记录。
- `issues` 每项只需 `{severity, location, problem, evidence, fix}`。`severity` 用 `must-fix`、`evidence-gap`、`optional`；位置指出具体 slug 字段或组件文件行。必改项未解决时为 needs-revision；缺少决定性证据、无法确认时为 unverified。无问题写空数组，不虚构修改。
- `followUp` 只写未决的具体动作。复审记录用 `recheckOf` 指向上轮 `<eventDate>/<slug>#<round>`，明确已改问题及仍存在的问题；不能把作者称已修改当成实际复读。
- `readObjects` 只列实际打开并完整读过的对象。article 哈希覆盖完整文章对象，包括 body、所有 sections、旧 explainer 和来源；design 哈希覆盖整条配置，包括 rationale。不是用既有 `article.sourceHash` 代替本次对象哈希。
- JSON 对象哈希固定为 Python `json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False)` 的 UTF-8 字节 SHA-256；组件、样式、类型及共享控制文件用实际原始文件字节 SHA-256。统一前缀 `sha256:`，不用格式化前后的文件哈希互相比对。
- 哈希须来自**同一份实际审读快照**。读完批次后复算当前对象；若在并行实现中已变化，标记旧结论不适用于新版本并重读受影响部分，不能把旧通过搬给新文件。仅计算哈希、导出清单或跑机械检查都不算读过。
- 共享依赖单独记实际路径、完整文件哈希和审读要点，再由 sharedReadRef 引用；其变化需复核实际受影响场景及文章，不因组件名称相同就沿用旧通过。新增使用的一手网页、术语定义或源图也记录实际读取对象与摘要，未取得则如实列 evidence-gap。
- `browser.status` 保持 not-reviewed，直到主代理交来可定位本篇或场景、宽度、操作及版本的实际证据；引用时注明操作由主代理执行。静态推断不能填为真实浏览器通过，也不自行另开浏览器。

## 按日收尾与覆盖

每个事件日实际配置到齐后，逐篇实读并报告具体 slug 的问题；必改修正后实际复读，再给该日各篇最终结论。某日存在未决项就保留在该日记录，不把后面的批次完成数覆盖它。后续日期由主代理通知，不提前假设通过。

覆盖清单只对基线 slug 集合做对应：待审、needs-revision、unverified、当前哈希静态 passed 分开计数；每篇以最新有效轮次为准，复审多轮不增加文章数。另列缺配置、孤立配置、日期不符、正文或组件变化导致的过期结论。最终应为 465 个唯一 slug 全部有当前有效记录，而非 465 行日志。

构建、真实浏览器截图与操作、开发环境集成及部署由主代理按实际授权完成并记录。本角色不写 DP、不改新闻或组件、不另派智能体，也不为本计划运行应用构建或扩大测试。
